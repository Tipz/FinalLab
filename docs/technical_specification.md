# Техническое задание: сравнение вариантов семейной поездки

Статус: обязательные US-01–US-10 и бюджетные US-14/US-15 реализованы.
Документ применяется вместе с [требованиями к backend](backend_requirements.md)
и [пользовательскими историями](user_stories.md). Интеграции описаны в
[отдельном документе](integration_documentation.md), правила лимита и резерва —
в [бюджетном планировании](budget_planning.md). Итоговые результаты и матрица
приёмки: [отчёт проекта](../development_report.md).

## 1. Описание проекта

Адаптивное веб-приложение помогает семьям с детьми вручную собрать варианты одной поездки и сравнить направления и жильё по полному бюджету, дороге и удобствам. Основные экраны: «Мои поездки» (`/`), «Варианты поездки» (`/trips/{id}/variants`) и «Сравнение» (`/trips/{id}/comparison`). На экране сравнения сохранена [концепция 3 «План поездки»](ui_concepts/03-analytical.html): таблица расположена перед компактными карточками выбранных вариантов с разбивкой расходов. Вход/регистрация (`/login`), диалоги редакторов и служебная страница «не найдено» не учитываются как основные экраны. Навигация и проверки описаны в [screen_navigation.md](screen_navigation.md).

Основания: [итоговый отчёт проекта](../development_report.md), [архив проектирования](history/project_description.md), [сравнение UI-концепций](history/ui_description.md), [карта историй и критерии приёмки](user_stories.md).

## 2. Целевая аудитория

Родитель-планировщик собирает предложения, оценивает расходы и актуализирует данные после входа в личную учётную запись. Второй родитель участвует в обсуждении через совместный просмотр. Состав семьи и возраст детей помогают выбрать нужные условия. Прикладных ролей доступа нет: авторизация основана на принадлежности поездки пользователю.

## 3. Объём MVP и принятые решения

- Обязательны истории US-01–US-10: параметры поездки, карточки вариантов, расчёт бюджета, сравнение и восстановление сохранённых данных.
- Все данные вводятся вручную. Суммы — в рублях за всю семью за весь период поездки.
- Доступны регистрация, вход и серверное хранение в PostgreSQL через API. Совместное редактирование в реальном времени не входит в объём.
- Автоматический поиск, обновление цен, бронирование, оплата и конвертация валют не входят в объём.
- US-11–US-12 (копирование и сортировка) — Should have, US-13 (отметка решения) — Nice to have. Их критерии документированы, но не входят в обязательную приёмку MVP.

Далее заданы действующие продуктовые правила. Серверное хранение определяют
FR-06 и [требования к backend](backend_requirements.md); сохранение выполняется
явным действием пользователя, поездки независимы друг от друга.

## 4. Данные и валидация

### Поездка

| Поле | Правило |
| --- | --- |
| id | Уникальный стабильный идентификатор |
| name | Обязательно, 1–100 символов после удаления пробелов по краям |
| startDate, endDate | Обязательные календарные даты; окончание строго позже начала |
| nights | Вычисляемая разность календарных дат, без влияния часового пояса и перехода на летнее время |
| adults | Целое число 1–10 |
| budgetLimitKopecks | Необязательный лимит за всю семью за всю поездку: 0–10 000 000 000 копеек; null — лимит не задан |
| reservePercent | Целый процент 0–100 от расходов каждого варианта; по умолчанию 0 |
| childAges | От 1 до 10 значений, каждое — целое число 0–17; 0 означает возраст менее года |
| selectedVariantIds | Идентификаторы выбранных вариантов только этой поездки |
| selectedCriteria | Подмножество семи фиксированных критериев |
| createdAt, updatedAt, revision | Время создания, изменения и версия записи для контроля изменений |

Приложение ориентировано на семьи с детьми: в текущем MVP требуется минимум один ребёнок. Возраст фиксируется пользователем для планируемой поездки; даты рождения и имена детей не собираются.

### Вариант

| Поле | Правило |
| --- | --- |
| id, tripId | Собственный идентификатор и ссылка на существующую поездку |
| name, destination, accommodation | Обязательные строки по 1–150 символов после удаления крайних пробелов |
| sourceUrl | Необязательно, до 2048 символов, только абсолютная ссылка http или https |
| roadDescription, notes | Необязательные строки до 2000 символов каждая |
| travelMinutes | Время в одну сторону: целое 0–100 000 или null; ввод часами и минутами, минуты 0–59 |
| transfers | Целое 0–20 или null |
| kitchen, crib, playground | Одно из значений yes / no / unknown; по умолчанию unknown |
| distanceMeters, distanceTarget | Целое 0–1 000 000 и описание цели 1–100 символов; либо оба отсутствуют |
| expenses | Шесть фиксированных статей, каждая — сумма в копейках или null |
| needsBudgetReview | Признак необходимости проверить расходы после изменения параметров поездки |
| createdAt, updatedAt, revision | Время создания, изменения и версия |

Статьи expenses: дорога туда и обратно, проживание, питание, местный транспорт и трансферы, развлечения, прочее. Допустимая сумма каждой статьи: 0–100 000 000 ₽, не более двух знаков после десятичного разделителя. Принимаются точка или запятая; группирующие пробелы допускаются. Пустое поле преобразуется в null. Буквы, отрицательные значения, бесконечность и лишние дробные знаки отклоняются. Внутренние расчёты выполняются в целых копейках; отображение — с русской группировкой разрядов и знаком ₽.

Итог и число ночей вычисляются, а не редактируются. Бюджет полный только при наличии всех шести статей. При неполном бюджете сумма известных значений показывается с явной пометкой; если не введена ни одна сумма, показывается «Бюджет не заполнен». Итог не отражает актуальные цены поставщиков.

## 5. Функциональные требования

### FR-01. Параметры и выбор поездки — US-01, US-10

При первом открытии «Моих поездок» в пустом хранилище создать вымышленную демонстрационную поездку с тремя заполненными вариантами и показать её в списке. Существующие поездки не перезаписывать. Для непустого хранилища предусмотреть действие «Добавить пример», которое не создаёт дубликат. Создание новой поездки после успешного сохранения открывает её экран вариантов. При наличии нескольких поездок предусмотреть переключатель по названию; он меняет идентификатор в URL, сохраняя раздел (варианты или сравнение). Карточки и сравнение относятся только к поездке из URL; неизвестный идентификатор не заменяется первой доступной поездкой.

Форма позволяет задать и редактировать поля поездки. Число детей соответствует длине списка возрастов, число ночей рассчитывается по датам. Изменение дат, числа взрослых или возрастного состава детей сохраняет ранее введённые суммы, но помечает все варианты needsBudgetReview. На карточке и рядом с бюджетом в таблице показывать «Проверьте расходы после изменения поездки». Снять пометку можно действием «Расходы проверены» в форме конкретного варианта. Изменение только названия поездки не требует проверки бюджетов.

### FR-02. Карточки и формы вариантов — US-02–US-04

Предоставить «Добавить вариант», «Редактировать» и «Удалить». Поддерживать разные направления, одинаковые направления с разным жильём и совпадающие названия: идентичность определяется id. Автоматически импортировать данные по ссылке нельзя.

Форма разделена на сведения о варианте, дорогу и удобства, расходы, заметки. Обязательные поля подписаны. «Сохранить» валидирует поля и записывает изменение; «Отмена» отменяет правки. При попытке закрыть форму с изменениями спросить, отбросить ли их или продолжить редактирование. После успеха карточка и сравнение обновляются одновременно.

Удаление требует подтверждения с названием варианта. В одной операции удалить вариант и его идентификатор из выбранных столбцов. При неуспешной записи вариант остаётся. Удаление последнего варианта показывает пустое состояние, но сохраняет параметры поездки.

### FR-03. Бюджет — US-05–US-06

Подписывать суммы «₽ за всю семью за всю поездку», дорогу — «туда и обратно». Считать сумму известных расходов при вводе корректных значений в форме; окончательные карточка и таблица обновляются после успешного сохранения. Недопустимое поле исключает сохранение формы и не подменяется нулём.

Показывать полный итог либо известную часть с пометкой неполноты и перечнем отсутствующих статей. При неизвестных всех статьях выводить «Бюджет не заполнен». Явный ноль — заполненное значение. Раскрытие бюджета показывает все шесть статей, включая нулевые и неизвестные. Состояния «неполный» и «требует проверки» независимы и могут отображаться одновременно.

### FR-04. Сравнение — US-07–US-08

В каждой карточке предусмотреть выбор для сравнения и обозначение числа выбранных вариантов у таблицы. По умолчанию новые варианты не выбраны. Для таблицы нужно минимум два выбранных варианта; меньшее количество сопровождается подсказкой. Снятие выбора не удаляет данные.

Таблица показывает выбранные варианты текущей поездки в порядке создания. Семь критериев включены по умолчанию: бюджет, время в одну сторону, пересадки, кухня, кроватка, площадка, расстояние до выбранной цели. Переключатели скрывают и возвращают строки. При выключении всех строк показывать подсказку, сохраняя выбор вариантов.

Неизвестные значения отображать как «Не указано», а отрицательное наличие удобства — «Нет». Расстояние выводить вместе с целью для каждого варианта. Не объявлять автоматически лучший вариант: цели расстояния и предпочтения семьи могут различаться. Сохранить набор критериев и выбранных вариантов отдельно для каждой поездки.

### FR-05. Просмотр на телефоне — US-09

На экране «Сравнение» сохранить композицию концепции 3: параметры поездки, затем таблица, затем карточки выбранных вариантов. Экран «Варианты поездки» показывает все карточки и переход к сравнению перед ними. На узком экране перенести боковую навигацию над содержимым, сохранив доступ ко всем трём экранам; формы и карточки расположить в одну колонку. В таблице использовать внутреннюю прокрутку с доступными названиями вариантов и критериев: закреплённая строка заголовков в области прокрутки и закреплённая первая колонка. Дать понятную визуальную подсказку о горизонтальной прокрутке. Возле пустого сравнения оставить добавление варианта и переход к выбору карточек на экране вариантов.

### FR-06. Серверное сохранение — US-10

Использовать защищённый HTTP API и PostgreSQL для поездок и вариантов. Данные принадлежат аутентифицированному пользователю и восстанавливаются после входа с другого браузера или устройства. IndexedDB может использоваться только как источник добровольного импорта прежних локальных данных и не является основным хранилищем.

Изменения форм записываются только через «Сохранить». Настройки сравнения записываются сразу после переключения. Подтверждать успех только после завершения транзакции. При ошибке записи формы оставить правки доступными; при ошибке записи переключателей вернуть прежнее состояние и показать сообщение.

При запуске проверить действующий сеанс и загрузить данные пользователя. Ошибки `401`, валидации, конфликта и недоступности сервера показывать раздельно. Повторное чтение доступно кнопкой «Повторить». Серверные миграции схемы должны сохранять ранее записанные данные.

Каждое изменение проверяет revision в транзакции на сервере. Если данные изменились в другой вкладке или на другом устройстве, API возвращает `409 Conflict`; несохранённые поля остаются видимыми для ручного переноса. Действие загрузки с потерей правок требует подтверждения. Это предотвращает незаметное перезаписывание данных.

На первом экране показывать состояние входа и недоступности сервера. При обнаружении старых данных IndexedDB предложить явный импорт, не отправлять и не удалять их автоматически. Совместное редактирование и пользовательский экспорт резервной копии не входят в MVP.

### FR-07. Лимит и резерв — US-14

В параметрах поездки задаются лимит бюджета в рублях и процент резерва. Пустой лимит отличается от нулевого. Резерв каждого варианта равен сумме известных расходов, умноженной на процент и округлённой вверх до целой копейки. Суммы разных вариантов не складываются.

Карточки и строка бюджета в сравнении показывают расходы, резерв, сумму с резервом и остаток либо превышение лимита. При полном проверенном бюджете сумма ниже лимита означает остаток, равная лимиту — отсутствие свободного остатка. Неполный бюджет или needsBudgetReview не позволяют объявить вариант укладывающимся в лимит. Превышение по известным расходам показывается сразу, даже при неполном бюджете. Если суммы вообще не заполнены, оценка лимита не выводится как ноль.

Изменение только лимита или резерва не изменяет расходы и не устанавливает needsBudgetReview. Сохранение и конфликты подчиняются FR-06. Подробные правила и проверки: [бюджетное планирование](budget_planning.md).

### FR-08. Что уточнить — US-15

Для каждого варианта автоматически формируется список: отсутствующие статьи расходов, напоминание о проверке после изменения поездки, неизвестные характеристики включённых критериев сравнения. Расходы стоят первыми и показываются независимо от включения критерия «Бюджет». Неизвестная характеристика выключенного критерия не создаёт уточнение. Ответ «Нет» и числовой ноль считаются заполненными.

Каждый пункт открывает редактор соответствующего варианта с фокусом на нужном поле. После успешного сохранения заполненного значения пункт исчезает. «Расходы проверены» требует явной отметки. Список вычисляется по сохранённым данным и отдельно в базе не хранится; ошибки API не изменяют его.

## 6. Нефункциональные требования по функциям

Показатели ниже — цели приёмки будущей реализации, а не результаты измерений текущих концепций. Контрольный набор: 10 поездок по 50 вариантов, до 10 одновременно сравниваемых столбцов. Это объём проверки быстродействия, а не ограничение количества данных в интерфейсе.

| Область | Проверяемое требование |
| --- | --- |
| FR-01, параметры поездки | Подписи связаны с полями; ошибки доступны без опоры только на цвет. Календарный расчёт числа ночей одинаков при разных часовых поясах |
| FR-02, карточки | После успешного ответа API карточка и таблица обновляются не позднее 300 мс без учёта сетевой задержки; удаление и очистка выбора атомарны |
| FR-03, бюджет | Расчёт в целых копейках, без накопления дробной ошибки; пересчёт корректного ввода не позднее 100 мс после события изменения |
| FR-04, сравнение | Переключение строки или столбца не позднее 200 мс; неизменённые значения не теряются; метки неизвестных значений доступны текстом |
| FR-05, адаптивность | Проверить ширины 360, 768 и 1440 CSS-пикселей и масштаб 200%; без горизонтальной прокрутки всей страницы, перекрытия полей и недоступных действий |
| FR-05, доступность | Все действия доступны клавиатурой, фокус видим; обычный текст имеет контраст не ниже 4,5:1; интерактивные цели не меньше 44×44 CSS-пикселей; диалог возвращает фокус инициатору |
| FR-06, хранение | Успех показывается только после успешной транзакции. Перезапуск не меняет успешно сохранённые значения. Невозможность чтения/записи не приводит к автоматическому удалению данных |
| Все функции | Приёмка в двух браузерных движках: Chromium и Firefox, с фиксацией версий в отчёте; интерфейс русскоязычный |
| Все функции | Пользовательский текст выводится как текст, а не исполняемая HTML-разметка. Ссылка на предложение открывается отдельно без доступа к исходному окну; неподдерживаемые схемы запрещены |
| Все функции | Локальные расчёты не требуют внешних сервисов. Поездки, возраст детей и заметки отправляются только в собственный backend приложения и не передаются аналитике или сторонним API |

Офлайн-перезапуск и офлайн-сохранение не обещаются. При отключении сети открытый черновик и локальный расчёт остаются доступны, но сохранение требует восстановления связи с API.

## 7. Обработка ошибок и UX (шаг 5)

Список сценариев сформирован с помощью AI-ассистента. В таблице указаны реакции интерфейса и сохранность данных, а не только тексты ошибок.

| Случай / связанные функции | Поведение интерфейса | Данные и восстановление |
| --- | --- | --- |
| Неверные даты, состав семьи — FR-01 | Ошибка под полем; фокус на первом неверном поле после попытки сохранения | Не сохранять; введённые значения остаются |
| Изменились даты или семья — FR-01, FR-03 | Пометка проверки расходов на каждом варианте | Суммы не пересчитывать пропорционально и не удалять; снять пометку после ручной проверки |
| Не заполнены название, направление или жильё — FR-02 | Указать конкретные обязательные поля | Не создавать вариант; сохранить черновик в открытой форме |
| Неверная ссылка или характеристика — FR-02 | Ошибка поля с допустимым форматом | Не открывать запрещённую ссылку; дать исправить значение |
| Отрицательная, слишком большая или неверно записанная сумма — FR-03 | Ошибка соответствующей статьи | Не сохранять и не округлять молча |
| Неизвестный расход — FR-03 | «Неполный бюджет» и список пропущенных статей; если неизвестны все — «Бюджет не заполнен» | null остаётся неизвестным, 0 означает подтверждённый ноль |
| Неизвестное удобство, дорога или расстояние — FR-02, FR-04 | «Не указано» | Не заменять на «Нет» или 0 |
| Поездок нет — FR-01 | Создать и открыть явно обозначенную вымышленную поездку с тремя вариантами | Заполнять только действительно пустую базу; существующие и повреждённые данные не перезаписывать |
| Нет вариантов — FR-02, FR-04 | «Пока нет вариантов» и «Добавить вариант» | Параметры поездки сохраняются |
| Для сравнения выбрано меньше двух — FR-04 | «Выберите минимум два варианта»; действие добавления или выбора | Не удалять существующий выбор |
| Выключены все критерии — FR-04 | «Выберите хотя бы один критерий» рядом с переключателями | Сохранить выбранные варианты |
| Ошибка API или БД — FR-02, FR-06 | «Не удалось сохранить данные на сервере», «Повторить» | Не объявлять успех; формы сохраняют правки в памяти, удаление не применяется; настройки сравнения откатываются |
| Некорректный ответ или несовместимая версия API — FR-06 | Сообщение о невозможности чтения, «Повторить» | Не заменять отображаемые данные пустым набором и не отбрасывать открытый черновик |
| Изменение из другой вкладки или устройства — FR-06 | «Данные уже изменились»; предложение загрузить текущую версию | API возвращает `409`, данные не перезаписываются; перед потерей правок спросить подтверждение |
| Сеть пропала после загрузки — FR-06 | Локальные формы и расчёт продолжают работать, сохранение сообщает о недоступности сервера | Черновик остаётся в памяти до повторной попытки или подтверждённого закрытия |
| Нет сети при первом открытии — запуск | Если ресурсы не загружены, доступна стандартная ошибка браузера; иначе приложение показывает недоступность API и повторную попытку | Серверные данные не изменяются, демонстрационная поездка поверх них не создаётся |
| Внешняя ссылка недоступна — FR-02 | Ссылка открыта отдельно; ошибка отображается внешним сайтом или браузером | Исходное приложение и поездка остаются открытыми; приложение не имитирует диагностику чужого сайта |
| Неавторизованный доступ — все функции | Показать экран входа; для истёкшего сеанса объяснить необходимость повторного входа | API возвращает `401`, не раскрывает данные и не применяет изменение |
| Доступ к чужому идентификатору — все функции | Показать, что объект не найден | API возвращает `404`, не раскрывает существование и содержимое чужой записи |

Обязательный MVP принимается по AC-01–AC-10; бюджетное дополнение — также по критериям US-14/US-15. Для обеих частей обязательны правила данных, нефункциональные требования и сценарии ошибок раздела 7. Проверить оба случая: разные направления и разное жильё в одном направлении. Суммы из UI-концепций служат контрольным примером: 143 000, 150 000 и 150 000 ₽.

При реализации нужны проверки расчёта и валидации, атомарного сохранения/удаления, восстановления и конфликта вкладок, а также проверка основных путей в браузере. Ошибки хранилища необходимо воспроизводить управляемо; отсутствие ошибки при обычном сохранении не доказывает корректную обработку отказа.
