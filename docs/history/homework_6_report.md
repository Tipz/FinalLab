# Отчёт о выполнении домашнего задания № 6

Проект «Вместе в путь» является учебным клиент-серверным приложением на базе
standalone Blazor WebAssembly, ASP.NET Core Minimal API, ASP.NET Core Identity,
EF Core и PostgreSQL.

Отчёт фиксирует результаты ДЗ № 6 на 23.09.2026 с актуализацией сведений
о развёртывании от 14.10.2026. Дополнение US-14/US-15 описано в
[budget_planning.md](../budget_planning.md) и развёрнуто 13.10.2026.
Публичный сайт: **[https://together.2-26-49-210.sslip.io/](https://together.2-26-49-210.sslip.io/)**.

## CI/CD

Для проекта настроен GitHub Actions pipeline, который при изменениях в ветке
`main` выполняет:

- восстановление зависимостей в locked mode;
- проверку форматирования;
- аудит NuGet-зависимостей;
- Release-сборку;
- модульные, компонентные и интеграционные тесты;
- запуск Docker Compose и браузерного Chromium smoke-теста;
- CodeQL-анализ;
- сборку multi-platform Docker image для `linux/amd64` и `linux/arm64`;
- публикацию образа в `ghcr.io/tipz/together`;
- smoke-проверку опубликованного образа.

В ревизии от 12.10.2026 CodeQL стал первым обязательным job: ошибки анализа и неподавленные SARIF findings блокируют проверки и публикацию. Format, NuGet audit, Release, xUnit и backend smoke объединены в `quality`. Подробности и ограничения локальных проверок: [ci_revision.md](../ci_revision.md). Сентябрьский GitHub run ниже относится к предыдущему workflow.

Автоматическое развёртывание выполняется через GitHub Actions и Komodo/Renovate.
GitHub Actions проверяет код и публикует образ в GHCR; Komodo/Renovate
обеспечивают обновление образа и deployment приложения.
Миграции базы данных выполняются отдельным одноразовым заданием до запуска
приложения. PostgreSQL и ключи Data Protection сохраняются между обновлениями.
Подробнее: [документация развёртывания](../manual_production_deployment.md).

## Развёртывание

С 13.10.2026 приложение опубликовано по адресу
[https://together.2-26-49-210.sslip.io/](https://together.2-26-49-210.sslip.io/).
Регистрация и аутентификация выполняются самим приложением.

Для запуска в другом окружении необходимо дополнительно настроить:

1. Docker и Docker Compose.
2. HTTPS reverse proxy.
3. Доверенный HTTPS-сертификат.
4. Production URL приложения.
5. Redirect URI в настройках приложения Яндекс ID.
6. Переменные `YANDEX_CLIENT_ID` и `YANDEX_CLIENT_SECRET`.
7. Номер счётчика `YANDEX_METRIKA_COUNTER_ID`.
8. Пароль PostgreSQL и остальные production-параметры.

Секретные значения не включаются в Docker image и клиентский Blazor bundle. Они
передаются backend-приложению через переменные окружения или secret store целевой
инфраструктуры.

## Интеграция Яндекс ID

В проекте реализована OAuth 2.0 авторизация через Яндекс ID на backend.

Реализация включает:

- Authorization Code Flow;
- PKCE;
- проверку OAuth state/correlation стандартными механизмами ASP.NET Core;
- получение идентификатора и email пользователя;
- создание локальной учётной записи;
- повторный вход существующего пользователя;
- обработку отмены и ошибок OAuth;
- защиту от внешнего `returnUrl`;
- запрет автоматического связывания с существующей учётной записью только по
  совпавшему email;
- отсутствие сохранения OAuth access token;
- сохранение обычной регистрации и входа по паролю.

Интеграция была проверена на локальном HTTPS-стенде. При переносе проекта
требуется создать или перенастроить приложение в консоли Яндекс ID и
зарегистрировать Redirect URI нового окружения.

Для публичного сайта используется
`https://together.2-26-49-210.sslip.io/signin-yandex`.
13.10.2026 развёрнуты исправления конфигурации и свойств external authentication.
Полный вход с реальным аккаунтом после обновления требует проверки пользователем;
backend smoke проверяет собственную регистрацию и вход по паролю.
Подробности: [отчёт OAuth](../yandex_oauth_configuration_fix.md).

## Интеграция Яндекс Метрики

На frontend интегрирована Яндекс Метрика.

Особенности реализации:

- код Метрики загружается только после явного согласия пользователя;
- согласие можно отозвать;
- передаваемый путь очищается от query string и fragment;
- данные поездок, заметки, email и идентификаторы пользователей не отправляются;
- разрешён только фиксированный набор событий;
- реализованы события успешного входа и создания поездки;
- параметры событий ограничены allowlist.

На локальном стенде использовался настроенный счётчик. В другом окружении
требуется указать собственный `YANDEX_METRIKA_COUNTER_ID` и проверить поступление
событий в интерфейсе Метрики.

## Безопасность

Для проекта проведён аудит безопасности с использованием AI-инструментов и
сопоставлением с OWASP Top 10.

В приложение добавлены:

- antiforgery-защита изменяющих API-запросов;
- CSP и другие security headers;
- HttpOnly, SameSite и Secure cookies;
- защита от open redirect;
- параметризованные запросы EF Core;
- проверка принадлежности данных пользователю;
- rate limiting для authentication endpoints;
- блокировка учётной записи после повторных неудачных входов;
- защита от перезаписи данных через revision и ответ `409 Conflict`;
- запуск приложения в контейнере от непривилегированного пользователя;
- read-only root filesystem;
- отдельное хранение ключей Data Protection;
- аудит прямых и транзитивных NuGet-зависимостей;
- CodeQL-анализ.

Найденные проблемы, внесённые исправления и оставшиеся инфраструктурные
ограничения описаны в `docs/security_audit.md`.

## Мониторинг и логирование

Приложение предоставляет два endpoint:

- `/health` — проверка доступности процесса;
- `/health/ready` — проверка готовности приложения и подключения к PostgreSQL.

Docker image и Compose используют health checks для контроля состояния контейнеров.

Логирование выполняется в JSON-формате в стандартный вывод контейнера. Записи
содержат время, уровень, категорию, Event ID и Trace ID. Docker ограничивает
размер и количество файлов логов.

AI-анализ типичного отказа readiness выполнен на синтетических обезличенных
данных и задокументирован в `docs/log_analysis.md`. Пользовательские данные,
секреты и реальные production-логи во внешние AI-сервисы не передавались.

## Итог

Все основные программные требования домашнего задания реализованы: CI,
тестирование, публикация Docker image, OAuth 2.0, аналитика, аудит безопасности,
health checks, структурированные логи и документация.

Приложение доступно по публичному HTTPS-адресу. Автоматическое развёртывание
выполняется через GitHub Actions и Komodo/Renovate.

Проект может быть перенесён в другое окружение с помощью опубликованного Docker
image и `docker-compose.deploy.yml`. Для полноценного запуска необходимо
предоставить reverse proxy, HTTPS, PostgreSQL и параметры собственных приложений
Яндекс ID и Яндекс Метрики.
