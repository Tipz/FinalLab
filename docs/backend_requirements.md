# Требования к backend и интеграции

Статус: утверждённая основа реализации. Документ дополняет продуктовые требования
из [технического задания](technical_specification.md). Основное хранилище —
PostgreSQL; доступ к данным требует входа в учётную запись.

## 1. Цель изменения

Существующий standalone Blazor WebAssembly-клиент должен работать с реальными
данными через защищённый HTTP API. Поездки сохраняются в PostgreSQL и доступны
пользователю после входа с другого браузера или устройства. Расчёты, валидация и
интерфейс US-01–US-10 сохраняют прежнее поведение, если ниже явно не указано иное.

## 2. Выбранная архитектура

- Frontend: существующий `Together.Client`, Blazor WebAssembly, .NET 10 и MudBlazor.
- Домен: `Together.Core` без зависимости от UI, браузера и базы данных.
- Backend: ASP.NET Core Minimal API `Together.Api` на .NET 10.
- Данные: PostgreSQL, доступ к данным через EF Core и Npgsql, схема через миграции.
- Пользователи: ASP.NET Core Identity; отдельные прикладные роли не требуются.
- Развёртывание: self-hosted Docker Compose. В production API и опубликованный
  frontend доступны с одного HTTPS-origin; отдельные origin разрешены только для
  локальной разработки.

Self-hosted выбран, чтобы оставить данные поездок, возраст детей и заметки в
инфраструктуре владельца приложения, сохранить единый C#/.NET-стек и представить
проверяемые backend-код, миграции и конфигурацию в репозитории.

## 3. Данные и владение

Каждая поездка принадлежит ровно одному аутентифицированному пользователю. Вариант,
возраст ребёнка, расход и настройка сравнения принадлежат поездке и отдельно между
пользователями не разделяются. Пользователь получает и изменяет только собственные
поездки. Запрос к чужому идентификатору возвращает `404`, чтобы не раскрывать факт
существования записи.

Реализованные таблицы:

- таблицы ASP.NET Core Identity для пользователей и сеансов;
- `trips` — параметры поездки, владелец, время создания и изменения, `revision`;
- `trip_children` — упорядоченные возраста детей;
- `variants` — сведения о варианте и его `revision`;
- `variant_expenses` — шесть фиксированных категорий и nullable-сумма в копейках;
- `trip_selected_variants` — выбранные для сравнения варианты;
- `trip_selected_criteria` — выбранные критерии сравнения.

Даты поездки хранятся как `date`, денежные значения — как `bigint` в целых
копейках. `NULL` означает неизвестное значение, `0` — подтверждённый ноль. Ограничения
диапазонов и допустимые справочные значения проверяются и в домене, и на сервере;
критичные инварианты дополнительно закрепляются ограничениями БД.

## 4. Аутентификация и безопасность

- Обязательны регистрация, вход, выход и получение текущего пользователя.
- Пароли никогда не хранятся и не логируются в открытом виде; хеширование выполняет
  ASP.NET Core Identity.
- Production-аутентификация использует защищённую HttpOnly cookie одного origin.
- Изменяющие запросы защищаются от CSRF; CORS содержит только известные origin и не
  использует сочетание wildcard с credentials.
- Строки подключения, пароли и ключи поступают через переменные окружения или
  секрет-хранилище и не включаются в клиентский bundle либо Git.
- Сервер повторяет всю значимую валидацию и проверяет владельца каждой записи.
- Логи не содержат пароли, cookie, заметки, возраст детей и полные тела запросов.

## 5. API

Базовый контракт:

| Метод и маршрут | Назначение |
| --- | --- |
| `POST /api/auth/register` | Регистрация; сеанс создаётся последующим входом |
| `POST /api/auth/login?useCookies=true` | Вход и создание cookie-сеанса |
| `POST /api/auth/logout` | Выход |
| `GET /api/auth/me` | Текущий пользователь |
| `GET /api/trips` | Список поездок пользователя |
| `GET /api/trips/{id}` | Поездка с вариантами и настройками |
| `POST /api/trips` | Создать поездку |
| `PUT /api/trips/{id}` | Изменить поездку с проверкой revision |
| `DELETE /api/trips/{id}` | Удалить поездку |
| `POST /api/trips/{tripId}/variants` | Добавить вариант |
| `PUT /api/trips/{tripId}/variants/{id}` | Изменить вариант с проверкой revision |
| `DELETE /api/trips/{tripId}/variants/{id}` | Удалить вариант и очистить выбор |
| `PUT /api/trips/{id}/comparison` | Атомарно сохранить настройки сравнения |

Создание поездки/варианта возвращает `201`; регистрация — `200` без cookie-сеанса, затем клиент отдельно выполняет вход. Чтение и изменение возвращают `200` или `204`. Ошибки
возвращаются как Problem Details: `400` — неверные данные, `401` — нет действующего
сеанса, `404` — объект не найден или не принадлежит пользователю, `409` — конфликт
revision, `500` — непредвиденная серверная ошибка с correlation id.

## 6. Транзакции и конфликты

Изменение поездки, удаление варианта вместе с его выбором и запись настроек
сравнения выполняются транзакционно. Клиент передаёт ожидаемый `revision`; сервер
обновляет запись только при совпадении. При `409 Conflict` клиент оставляет черновик
в форме и предлагает загрузить актуальную версию. Перед отбрасыванием черновика
требуется подтверждение.

Интерфейс заменяет отображаемые сохранённые данные только после успешного ответа
API. Сетевой сбой, ошибка валидации или отказ транзакции не должны показывать
сообщение «Сохранено».

## 7. Переход с IndexedDB

IndexedDB перестаёт быть основным хранилищем. После первого успешного входа клиент
может обнаружить старый `Workspace` и предложить импорт. Импорт не запускается без
явного согласия и не удаляет локальную копию автоматически. Очистка локальных данных
доступна только отдельным подтверждаемым действием после успешной проверки импорта.

## 8. Развёртывание и эксплуатация

Репозиторий должен содержать Dockerfile, `docker-compose.yml`, `.env.example`,
миграции и проверку работоспособности API. PostgreSQL использует постоянный volume.
Документация описывает HTTPS reverse proxy, применение миграций, резервное
копирование и восстановление. Развёрнутый backend должен быть доступен frontend,
а данные должны сохраняться после перезапуска контейнеров.

Для переноса на другую инфраструктуру GitHub Actions публикует единый образ API и
Blazor-клиента в `ghcr.io/tipz/together` для `linux/amd64` и `linux/arm64`. Обязательны
неизменяемый SHA-тег, release-теги `v*`, OCI metadata и отдельный одноразовый запуск
миграций перед приложением. `latest` допускается как удобный указатель на `main`,
но не как единственный идентификатор production-релиза. Строка подключения и другие
секреты поступают только из secret store целевой инфраструктуры; ключи Data
Protection сохраняются на внешнем постоянном volume.

Отдельный `docker-compose.deploy.yml` должен разворачивать опубликованный образ без
исходников и SDK: поднять PostgreSQL, дождаться healthcheck, выполнить миграции и
запустить приложение. Порт БД наружу не публикуется; адрес и порт приложения,
image tag и cookie policy параметризуются через исключённый из Git env-файл.

## 9. Проверяемые критерии завершения

- Новый пользователь может зарегистрироваться, войти и выйти.
- Пользователь создаёт, читает, изменяет и удаляет свои поездки и варианты.
- Данные восстанавливаются после нового входа и перезапуска контейнеров.
- Два пользователя не видят и не изменяют данные друг друга.
- `null` и нулевой расход проходят полный путь UI → API → PostgreSQL → UI без
  смешения значений.
- Конкурирующее изменение возвращает `409` и не уничтожает черновик.
- Проверены ответы `400`, `401`, `404`, `409` и безопасный `500`.
- Проходят `dotnet build`, модульные, API и браузерные end-to-end тесты.
- `backend_documentation.md` содержит архитектуру, развёртывание, API, примеры
  запросов и фактически выполненные проверки, включая применение AI.

## 10. Вне текущего объёма

Разрешён один социальный вход: OAuth 2.0 через Яндекс ID как дополнительный
способ аутентификации с сохранением password login.
Другие OAuth-провайдеры, восстановление пароля через почту, роли администратора,
приглашения, совместное редактирование в реальном времени, автоматический импорт
цен, бронирование и оплата требуют отдельного решения.

## 11. Лимит бюджета и резерв

`TripWriteRequest` и `TripResponse` расширены полями `budgetLimitKopecks` (nullable bigint,
0–10 000 000 000 копеек) и `reservePercent` (integer, 0–100). Настройки сохраняются
существующими POST/PUT поездки с проверкой владельца и expectedRevision. API и
CHECK-ограничения PostgreSQL повторяют валидацию; отдельные маршруты не добавляются.

Миграция `20261012132837_TripBudgetSettings` сохраняет существующие записи и задаёт
лимит NULL, резерв 0%. Изменение только этих настроек не помечает расходы для
пересмотра. Расчёт оценки и список уточнений находятся в Together.Core; производные
результаты не записываются в БД. Старый добровольный импорт получает те же значения
по умолчанию. Правила и проверенные команды: [budget_planning.md](budget_planning.md).
