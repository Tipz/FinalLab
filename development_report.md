## 4. Архитектура и хранение

### Core

Trip и Variant содержат данные и версии. TripDraft и VariantDraft отвечают за правила ввода.
Budget принимает точку или запятую, группирующие пробелы и считает суммы в целых копейках.
Календарные ночи вычисляются через DateOnly. Неверные суммы не округляются автоматически.

### Client

Формы содержат отдельные черновики. Отмена не меняет сохранённый объект.
Обязательные поля имеют подписи; ошибки связаны с полями через aria-describedby,
после проверки фокус переходит на первое неверное поле.

MudBlazor применяется для темы, кнопок, уведомлений и индикатора загрузки.
Формы, таблица и нативный dialog используют семантический HTML и локальные стили.

### IndexedDB

Хранится один версионированный снимок. Это упрощает атомарное удаление варианта вместе с его выбором.
Внутри одной readwrite-транзакции проверяются revision снимка и изменяемой поездки.
Подтверждение UI происходит только на событии завершения транзакции.

При сохранении передаётся изменяемая поездка, а при переключении сравнения —
только настройки. JS объединяет изменение с текущим снимком внутри транзакции.
Незатронутые поездки не сериализуются повторно в .NET.

Перед использованием прочитанных данных проверяются обязательные поля, схема,
ограничения и связи идентификаторов. Неизвестная версия и повреждение не приводят к очистке базы.
В версии 1 предусмотрено атомарное создание схемы; миграций между несколькими выпущенными версиями пока нет.

Общая версия снимка намеренно консервативна: изменения разных поездок в разных вкладках
тоже могут вызвать конфликт. Черновик остаётся доступным для ручного переноса.

### Особенности окружения

Node.js/npm отсутствовали; для выбранного стека они не потребовались.
Playwright использует свой runtime и отдельные браузеры.

Параллельная пересборка уже запущенного тестового exe в Windows вызвала блокировку файла.
Проверки и сборки этого проекта далее выполнялись последовательно.
Массовая Release-сборка во время dotnet watch также вызвала предупреждения о переполнении файлового наблюдателя;
обычные изменения CSS затем успешно применились в открытом браузере за 98 и 2 мс.

SDK сообщил об отсутствии необязательной нагрузки wasm-tools.
dotnet publish завершился успешно; дополнительные WebAssembly-оптимизации не применялись.
Опубликованная сборка проверена отдельно.

## 7. Производительность

Набор: **10 поездок × 50 вариантов**, до **10 столбцов** в сравнении.
Измерения выполняются внутри браузера через performance.now и MutationObserver;
время запуска Playwright-команды не включается.

Переключение строки и столбца измеряется от DOM-события до изменения таблицы,
включая сохранение. Для строки одна первая итерация используется как прогрев.
Пересчёт бюджета измеряется от ввода до обновления суммы.
Обновление карточки измеряется от завершения IndexedDB-транзакции.

Проверяемые пределы: строки/столбцы ≤200 мс, бюджет ≤100 мс, обновление после записи ≤300 мс.
Полные значения каждого прогона: [performance.json](docs/evidence/performance.json).

Итоговый прогон, миллисекунды:

| Движок | Строка, максимум | Столбец, максимум | Пересчёт бюджета | Обновление после записи |
| --- | ---: | ---: | ---: | ---: |
| Chromium | 37,6 | 46,4 | 9,1 | 41,4 |
| Firefox | 113 | 97 | 27 | 130 |

Это локальные контрольные измерения, а не гарантия для любого устройства.
Проверка на физическом телефоне и длительное нагрузочное тестирование не проводились.

## 9. Выводы и дальнейшая сдача

### Дополнительная диагностика запуска на localhost:5180

После первоначальной сдачи пользователь сообщил об ошибке `Failed to start platform`
и HTTP 404 для `_framework/dotnet.f23dlrk55z.js`. Она воспроизведена в свежем Chromium:
[результат до исправления](docs/evidence/startup-before.json).

Причина — оставленный работающим процесс DevServer после последующих пересборок.
Процесс был запущен в 16:18:12, а файл карты статических ресурсов на диске обновлён
в 20:40:53. HTML уже ссылался на новую версию модуля, но сервер использовал прежние маршруты.
Сам файл модуля присутствовал на диске; очистка пользовательской базы не нужна.

Добавлена отдельная проверка `--startup`, которая проверяет живой сервер и его карту
импортов. Сервер перезапущен с актуальной сборкой через `dotnet watch`.
Повторная проверка прошла: все проверенные модули вернули 200, ошибок загрузки
и консоли нет, форма создания поездки открывается и закрывается.
Служебная навигация hot reload с HTTP 204 записывается отдельно от ошибок.
Результат: [startup-after.json](docs/evidence/startup-after.json).

Запрошенный MCP Chrome DevTools отсутствовал среди доступных инструментов сессии.
Для воспроизведения использован Chromium через Playwright, с записью сетевых ошибок
и консоли. Предыдущие проверки опубликованной Release-сборки на порту 5181 не
обнаруживали рассогласование оставленного DevServer на другом порту.

### Проверка backend ДЗ № 5 на Linux-ВМ

17 сентября 2026 года production-образы собраны Docker Compose 2.39.1 и запущены
с PostgreSQL. Одноразовый сервис применил миграцию, healthcheck БД и
`/health/ready` прошли. HTTP smoke-сценарий подтвердил регистрацию, cookie-вход,
CRUD, optimistic concurrency, изоляцию владельцев и выход.

Первый прогон выявил ошибку `500` при создании варианта: EF считал сущность с заранее
назначенным Guid изменённой и пытался вставить расходы до существования родительской
строки. Вариант теперь явно добавляется в `DbSet`; добавлен регрессионный API-тест.
Повторный прогон на PostgreSQL вернул `201`, сохранив массив
`[100000, 0, null, 25000, null, 5000]` без потери различия нуля и неизвестной суммы.

Отдельный Playwright-сценарий `--backend-smoke` в Chromium прошёл регистрацию через
UI, создание серверного примера, повторную загрузку и выход. Результат находится в
[backend-browser-results.json](docs/evidence/backend-browser-results.json), снимок —
[backend-chromium.png](docs/evidence/backend-chromium.png). HTTPS и публичный домен
на локальном стенде не проверялись.

### GitHub Actions и контейнерный registry

В репозитории [Tipz/HT6](https://github.com/Tipz/HT6) настроены три workflow:

- `CI` собирает solution в Release и запускает 32 Core/UI- и 4 API-теста;
- `Backend browser smoke` поднимает Docker Compose с PostgreSQL и выполняет
  Chromium-сценарий текущей backend-версии;
- `Publish container image` публикует `ghcr.io/tipz/ht6` для `linux/amd64` и
  `linux/arm64`, добавляет OCI metadata, provenance и SBOM.

Все три workflow успешно прошли на коммите с multi-platform Dockerfile. Публичный
GHCR manifest проверен анонимным запросом и содержит обе целевые архитектуры. Образ
получает теги `latest`, `master`, `sha-*` и `v*`; для production рекомендуется
неизменяемый SHA- или release-тег. Публичный HTTPS-домен по-прежнему не развёрнут.
